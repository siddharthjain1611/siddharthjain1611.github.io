I designed and shipped

The internal systems had no interface an AI tool could call. Building the interface was the product decision; the server was just how I got there.

The problem

Nobody was going to build it for me.

There was no way for an AI assistant to read our internal systems. Not a bad interface, not a missing integration, no interface at all. Any request that needed real data meant a human went and pulled it by hand.

I needed that access for my own work, and I could see the same wall in front of anyone else trying to use these tools here. The obvious path was to file a platform request and wait. Platform teams are not staffed to build this for one PM, so that path had no end date.

The bottleneck was not the protocol. It was that no one owned the request, so no one was accountable for it landing.

So I owned it. I designed the surface, wrote the server, and deployed it. Three different clients talk to it now without any of them knowing anything about the underlying systems.

Design

Deciding what the model is allowed to ask for.

The interesting product problem was not the server. It was the boundary. A tool interface is a permission surface, and how you cut it determines what the model can go wrong at.

The first cut was too coarse. A single wide tool that could return a record turned every hallucinated argument into a confused result three steps later, with nothing in between to catch it. Narrowing it fixed most of that.

Decision Why
One tool per user intent, not per screen Matches the request a client can actually make, so arguments stay predictable and testable
Reads and writes separated Anything that changes state is a different tool with a different approval path from anything that reads
Errors return state, not prose A model that gets a structured error can recover from it. A model that gets a sentence has to guess
No tool that returns bulk data Large payloads blow the context window and the model's ability to reason about any of it

That last one cost me a rewrite. The first version paginated properly and I still should not have shipped it, because correct pagination is not the problem. The problem is that more tokens is worse than fewer tokens, regardless of how cleanly they arrive.

Architecture

An agent proposes, an evaluator checks,
a gate enforces.

The system runs in three parts: a primary agent that does the work, an evaluator that inspects the attempt, and an intercept gate that sits in front of every tool call and decides whether it is allowed to proceed.

PRIMARY AGENT

Produces the action

Reads context, decides what to do, proposes a tool call with its arguments.

EVALUATOR

Inspects the attempt

Reviews the proposed action against policy before it runs, and can reject it with a reason.

INTERCEPT GATE

Enforces at the boundary

The last checkpoint before execution. Non-bypassable, and independent of what the model believes about its own permissions.

The split matters because an evaluator that is part of the same reasoning pass as the generator is not really evaluating. It is agreeing with itself. Putting the gate outside that loop is what makes the constraint real rather than advisory.

A correction

I had the evaluator design backwards,
and it took a while to see it.

My first design ran the evaluator in parallel with the generator, on the same input, and treated the two as independent checks. The stated logic was that if neither flagged a policy violation, the action was safe.

That reasoning does not hold for output. Screening an input is genuinely a parallel operation, because the risk is in what came in. But if you want to know whether a generated answer violates policy, the evaluator has to see the answer. Two checks over the same input tell you the input was fine twice. They tell you nothing about what came out.

The rule I settled on: anything inspecting a produced artifact must be downstream of that artifact. Parallel checking is for inputs. If it cannot see the output, it cannot certify the output, and the confidence it reports is not evidence.

Reworking it into a sequential gate closed the gap. A small design change that changes the guarantee completely.

Delivery

What shipping it end to end
actually required.

No engineering handoff sounds like a shortcut. It is the opposite. Without a dedicated engineering reviewer, I had to design in everything a review would have caught.

Had to be right first time

  • Auth that does not leak a credential into a client config
  • Idempotency, because a retried write is worse than a failed one
  • Structured errors on every failure path, including the ones I hoped would not happen
  • Logging that identifies the caller without logging the payload

Had to be adoptable without me

  • Docs good enough that a PM can connect a client without me in the room
  • Failure modes explained, not hidden, so nobody blames the tool when the system is down
  • A clear boundary on what the server will never do, so nobody asks it to
  • Versioning from day one, because I would be living with my own interface

Building it myself was a deliberate trade, and I would make it again here: speed on the first version, paid for in review coverage I had to provide myself. The right call depends entirely on whether you are the bottleneck.

Where it went

What I would do with more runway.

  • Replace the coarse error contract with typed errors per tool, so a client can recover without parsing prose.
  • Put the tool-call trace in front of a human for a sampled share of writes, and use the disagreement rate as the eval set.
  • Publish the interface to a wider internal audience, which means auth and rate limiting become a real problem instead of a hypothetical one.
  • Version the protocol surface properly and write down what a deprecation looks like, before the first client depends on it.
